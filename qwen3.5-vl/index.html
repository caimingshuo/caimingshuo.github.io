0.1 什么是视觉语言模型

大语言模型（LLM）只会处理文字。你给它一段文本，它猜下一个 token。它看不见图片，听不见声音——它的世界里只有 token 序列。

视觉语言模型（Vision-Language Model, VLM）要解决的问题是：让同一个模型既能读文字，也能「看」图片和视频，并把两者放在同一个上下文里一起推理。你可以问它「这张图左上角红色框里写的是什么」「视频第 30 秒那个人拿起了什么」「根据这张架构图把代码补全」。这些问题的共同点是：答案必须同时来自视觉信息和语言推理，缺一个都答不出来。

实现 VLM 有两种路线，理解 Qwen3.5 的第一步就是知道它走哪条：

  • 外挂式：先训好一个纯语言模型，再额外训一个视觉编码器，用适配层把视觉特征「翻译」进语言模型的输入空间。视觉能力是后来接上去的。
  • 原生式（native）：从基座预训练开始，文本、图片、视频就混在一起训练。视觉不是翻译进来的第二语言，而是母语的一部分。Qwen3.5 官方博客标题里的「Towards Native Multimodal Agents」说的就是这个路线——视觉语言能力内建于基座，而非外挂。
为什么「原生」很重要

外挂式路线的天花板在于：视觉信息在「翻译」成语言模型能懂的表示时会丢东西，尤其是空间关系和细粒度细节——语言模型的输入空间是为文字优化的，不是为像素优化的。原生路线让模型从第一天起就学会「文字和像素是同一个世界里的两类证据」，这在需要精细视觉推理的任务上（文档版式、UI 操作、视频时序定位）差距会被放大。第 5 章你会看到，Qwen3.5 最强的项目恰好集中在这几类任务上，这不是巧合。

常见误解

「VLM = OCR 引擎 + LLM 拼接：先把图里的字识别出来，再让语言模型读。」

这是 2018 年以前的思路，不是现代 VLM。现代 VLM 不是把图「转成文字描述」再读，而是直接把图片的视觉特征和文字的 token 放进同一个序列里，让注意力机制自由地在图文之间互查。「图里没有字的部分」（布局、颜色、空间关系、动作）根本不会经过文字这道有损压缩。

0.2 一张图怎么变成 token

语言模型只认 token。所以一张图片要进入模型，必须先变成一串「视觉 token」。过程分三步：

  1. 切 patch：把图片切成规则的小方块（patch），比如每个 patch 是 16×16 像素。一张 448×448 的图会切成 28×28 = 784 个 patch。
  2. 视觉编码器（ViT）：Vision Transformer 把每个 patch 编码成一个向量——这就是视觉 token。ViT 内部也是 Transformer，只不过它的「词」是图片块。
  3. 压缩与对齐（merger）：把相邻的几个视觉 token 合并成一个（比如 2×2 合并，token 数减为四分之一），并投影到语言模型的向量维度上。出来的东西和文字 token 在形状上完全一样，可以混在同一个序列里。

最终，「一张图 + 一个问题」在模型眼里就是一个混合序列：[视觉token ×N][文字token：这张图上画了什么？]。视频同理：抽帧后每帧都按图片处理，只是还要额外编码「这是第几秒的帧」——这是第 3 章的主题。

打个比方

视觉 token 化像把一幅拼图按固定大小切成小块，每块贴上一张写有「这块大致是什么」的标签，然后把标签（而不是原图）交给一个只读过书的人去推理。merger 的 2×2 合并相当于把四张相邻标签浓缩成一张，省纸张但损失一点细节。

类比失效处：「标签上写着是什么」暗示视觉 token 里存的是人类可读的描述。实际上视觉 token 是高维向量，没有任何一维对应「红色」「圆形」这种可命名的属性；而且模型推理时随时可以回头「看原图」——注意力让每个文字 token 都能直接访问任意视觉 token 的原始向量，并不是只能靠标签转述。

有一个数字直觉你必须建立：视觉 token 很费额度。一张普通分辨率的图就是几百到上千个视觉 token；视频每秒抽若干帧，一分钟的视频就是上万 token。这就是为什么「256K~1M 的上下文」对视频理解不是卖点而是底线——第 8 章会算这笔账。

一句话记住：图片进模型 = 切块 → ViT 编码 → merger 压缩对齐，出来的视觉 token 和文字 token 住在同一个序列里。

自测题 0.1：一个 60 秒的视频，每秒抽 2 帧，每帧压缩后产生 256 个视觉 token。仅视频部分要占多少 token？如果模型上下文是 256K，视频占了多少比例？

（提示：这是最基础的「视频 token 爆炸」估算，后面第 8 章会反复用到这个技能。）

先想：三步乘法：秒数 × 每秒帧数 × 每帧 token 数。
关键在于：别漏掉「每秒 2 帧」——不是 60 帧，是 120 帧。
第一步这样走：60 × 2 = 120 帧；120 × 256 = ?
完整答案：60 × 2 × 256 = 30,720 个视觉 token。占 256K（262,144）的约 11.7%。注意这还只是一分钟的短视频、且每帧只算 256 token 的「温柔」假设——高分辨率帧可以到上千 token。一段 30 分钟的视频按同样参数就是约 92 万 token，256K 上下文直接装不下，这就是为什么托管版要默认 1M 上下文。
变式：如果上下文只有 32K，在不降低帧率的前提下，你只能靠「减少每帧 token 数」把这段 60 秒视频塞进去。每帧 token 数要压到多少以下？这种压缩的代价是什么？

0.3 MoE：总参数与激活参数

普通（稠密，Dense）模型里，每个 token 都要经过模型的全部参数。参数翻倍，计算量就翻倍——「大」和「贵」死死绑在一起。

混合专家（Mixture-of-Experts, MoE）解开了这个绑定：把每层的前馈网络复制成很多份（每份叫一个「专家」），加一个小「路由器」给当前 token 打分，只让得分最高的几个专家干活。Qwen3.5-397B-A17B 的名字就是这两个数字：总参数 397B，每个 token 只激活 17B——约 4.3%。

量含义Qwen3.5-397B-A17B决定什么

MoE 像一家有几百位专科医生的超级医院。你来看病，分诊台（路由器）看一眼症状，挑几位最对口的医生会诊。医院很大所以什么病都能治（总参数多 = 知识容量大），但你这次就诊只占用几位医生的时间（激活参数少 = 计算量小）。

类比失效处：比方暗示专家们有清晰分工（「这位看眼科」）。真实 MoE 里专家的分工是训练中自发形成的，往往不对应任何人类能命名的领域，而且负载天然不均——有的专家被挤爆，有的门可罗雀。另外，所有医生都得同时「在医院里待命」：全部 397B 参数必须常驻显存，因为你无法预知下一个 token 会路由到哪几位专家。MoE 省的是算力，不是显存。

一句话记住：397B 决定「它懂多少」，17B 决定「它说一个字多快多贵」。Qwen3.5 的速度秘密全在后一个数字里。

0.4 线性注意力 vs 全注意力

注意力机制让每个 token 回头查前面所有 token，这带来两个代价：

  1. 计算量随长度平方增长：n 个 token 要打约 n²/2 次分。
  2. KV 缓存随长度线性增长、且永不缩小：每生成一个新 token 都要回头查所有历史的 K、V，所以要把它们全存在显存里。上下文越长缓存越大。
▶ 交互演示 0-A：注意力打分热力图——「它」到底在看谁

例句：「猫 追 老 鼠 ， 它 饿 了」（8 个 token）。每个格子是「行 token 关注列 token」的权重，颜色越深权重越大；悬停任意格子看数值，点击左侧 token 高亮它的整行注意力分布。

怎么读这张图：看「它」那一行：最深的格子落在「猫」（0.62）上——模型解代词靠的不是语法规则，而是这行权重分布。再看「饿」那一行：「它」（0.43）和「猫」（0.35）都很深，因为「谁饿了」的答案藏在前面。两个要点：① 下三角之外全是空白——每个 token 只能看自己和左边（因果掩码），这就是语言模型「不能偷看未来」的几何形状；② 每行权重加起来等于 1——softmax 保证的，注意力本质是「按权重把别人的信息混进来」。本图权重为手工构造的教学示意数据，非真实模型输出，但分布形态（代词指向名词、标点就近聚集）是真实模型的典型样子。

长度涨 256 倍，注意力计算量涨 6.5 万倍。这就是纯全注意力模型做长视频理解根本跑不动的原因。

线性注意力换了一条路：不再为每个 token 单独存一份 K、V，而是维护一个固定大小的状态矩阵，每读一个 token 就把它的信息「揉」进状态里。不管你读了 4K 还是 1M 个 token，状态就那么大——显存占用是常数，每步计算量也是常数，总成本随长度线性增长而不是平方。

代价是什么？固定大小的状态是有损压缩：它记不住「第 12,345 个 token 的确切内容」这种精确定位信息，而全注意力的 KV 缓存是逐 token 无损的。所以现代高效架构几乎都用混合方案：大部分层用线性注意力控制成本，少部分层保留全注意力保住精确检索能力。Qwen3.5 继承的 Qwen3-Next 架构正是这样：Gated DeltaNet（线性注意力）+ Gated Attention（全注意力）混合。第 4 章会详细拆。

打个比方

全注意力像开会时把每个人的发言逐字记录在案，谁要引用就翻原话——精确，但会议越长记录越厚。线性注意力像只让一个记录员维护一块白板：每个人发言完，他把要点更新到白板上，旧内容不断被覆盖压缩——白板永远只有一块大，但你没法问他「第三个小时第二个人说的第三个词是什么」。

类比失效处：「白板」暗示状态是完全无序的摘要。实际上线性注意力的状态矩阵有精确的数学结构（key 维度 × value 维度），查询时是用当前的 q 去和状态做运算，能取回的信息比「要点摘要」系统得多——只是容量确实有限，且写入时会互相干扰。另外 DeltaNet 的「delta」规则意味着它可以有选择地擦除旧信息再写入，比单纯覆盖聪明，这是普通会议纪要比方装不下的。
自测题 0.2：某模型有 60 层全注意力层，每层每 token 的 KV 缓存为 4 KB。另有一个线性注意力变体，每层只维护一个固定 64 KB 的状态。(a) 256K 上下文下两者的「记忆」各占多少？(b) 为什么 Qwen3.5 不把 60 层全换成线性注意力？
先想：KV 缓存随 token 数涨，固定状态不随 token 数涨。分别算清楚再比较。
关键在于：(a) 问的是「记忆占用的显存」，不是计算量。注意单位换算：262,144 个 token × 每层 4 KB × 60 层。
第一步这样走：全注意力：262,144 × 4 KB = 1 GB（每层），再乘 60 层。线性注意力：64 KB × 60 层，与 token 数无关。
完整答案：(a) 全注意力 KV 缓存 = 262,144 × 4 KB × 60 = 60 GB；线性注意力状态 = 64 KB × 60 = 3.75 MB。相差约 16,000 倍——而且这个差距会随上下文变长继续拉大。(b) 因为固定状态记不住精确的逐 token 历史。像「把文档第 47 页第三行的数字和第 3 页的加起来」「视频第 30 秒出现的那个人穿什么衣服」这类任务，本质是对任意远位置的精确检索，只有全注意力的无损 KV 缓存做得到。所以 Qwen3-Next / Qwen3.5 的路线是混合：大部分层用 Gated DeltaNet 把成本压下去，保留一部分 Gated Attention 层负责精确查找。这不是折中主义，是让两种机制各干自己最擅长的事。
变式：假设混合比例是 3:1（45 层线性 + 15 层全注意力），同样 256K 上下文，KV 缓存总量是多少？和 60 层全注意力相比省了多少？
自测题 0.3：向一个完全不懂技术的朋友解释「为什么 Qwen3.5 能又大又快」。要求：不许用「参数」「token」这两个词。
先想：「大」对应生活里的什么概念（容量/藏书量）？「快」对应什么（每次办事要动用多少人手）？
关键在于：MoE 的核心是「总量」和「每次用量」脱钩——你的比方必须同时装下这两件事，还要装下它们的「解绑」。
第一步这样走：先造「大」的比方（一个藏书极多的图书馆），再造「快」的机制（每次提问只叫醒最相关的几位馆员），最后点破「藏书多 ≠ 每次都要全员出动」。

1.1 Qwen3.5 是什么

Qwen3.5 是阿里巴巴 Qwen 团队（通义千问）2026 年 2 月 16 日（除夕夜）发布的新一代旗舰模型系列，官方博客《Qwen3.5: Towards Native Multimodal Agents》于 2 月 17 日发出。三个关键事实：

  • 它是原生视觉-语言模型。不存在「Qwen3.5 语言版」和「Qwen3.5-VL 视觉版」两条产品线——视觉语言能力内建于基座。所以本站标题里的「Qwen3.5-VL」指的就是 Qwen3.5 本身。

2.1 数据流全景

主路径只有一句话：视觉 token 和文本 token 拼接成一个序列，送进同一个语言模型，逐 token 生成答案。三段各自的分工：

  1. ViT：不看文字，专心把图像 patch 编成一串视觉特征向量。它是唯一「见过像素」的部分。
  2. merger：把相邻 2×2 的视觉 token 合并 + 投影到语言模型的隐藏维度。两件事：省 token（数量降为 1/4），对齐空间（让视觉向量和文字向量量纲一致，能被同一个注意力处理）。
  3. 语言模型：Qwen3-Next 基座，混合注意力 + MoE + MTP（第 4 章详拆）。它对「这个 token 来自图还是来自字」没有特殊待遇——这正是原生多模态的含义。

怎么读这张图：橙色小方块是「数据包」，跟着它走一遍就是一张图进入模型的完整旅程。注意第④步：网格从 6×6「缩」成 3×3——merger 把 4 个相邻 patch 压成 1 个 token，token 数除以 4，这就是后面所有层成本省一个量级的地方。到了第⑤步，紫色（视觉）和灰色（文本）方块已经躺在同一支队伍里——对语言模型来说它们再无区别，这正是「原生多模态」的字面含义。

2.2 ViT 与 merger：压缩的艺术

merger 的 2×2 合并是一个典型且必要的折中：视觉 token 数直接决定进入语言模型的序列长度，而序列长度同时撞上第 0 章的两个代价（注意力计算、KV 缓存）。把 token 数压到 1/4，意味着后续所有层的成本低一个量级。代价是：合并之后，单个 token 对应原图 32×32 像素的区域，极小的文字、密集表格的细线这类信息可能被「平均掉」。

这个张力——要省 token，又怕丢细节——正是 DeepStack 要缓解的问题。

2.3 DeepStack：分层注入为什么比一次性注入好

传统做法（以 LLaVA 系为代表）是「一次性注入」：ViT 跑完，取最后一层的特征，过 merger，全部塞给语言模型的输入层。之后语言模型就只能基于这一份特征做推理。

问题在于 ViT 的不同层看到的本来就不一样：浅层特征偏局部细节（边缘、纹理、小字的笔画），深层特征偏全局语义（「这是一张发票」）。只取最后一层，等于只把「全局摘要」给了语言模型，细节在 ViT 内部就被丢掉了——深层网络的信息瓶颈。

DeepStack（Qwen3-VL 提出、Qwen3.5 继承）的做法：把 ViT 的多层级特征（浅、中、深）分别注入语言模型的多个中间层，而不是只在输入层给一次。语言模型在往深处推理的过程中，能不断「重新查阅」不同粒度的视觉信息——浅层细节在需要时被调出来（比如读小字、数格子），深层语义在理解整体时起作用。

打个比方

一次性注入像考试前只允许你交一份「全书内容提要」给考生，考试时不许翻书。DeepStack 像开卷考试，而且书里不同详略的章节（目录、章节摘要、正文细节）分别在不同的答题阶段允许翻阅——做细节题时翻正文，做主旨题时看目录。

类比失效处：开卷考试里「翻书」是人的主动动作；DeepStack 的注入是固定的结构连接——哪些 ViT 层接到 LLM 哪些层是架构设计好的，模型不能「想翻就翻」。它能做的是通过注意力权重决定「用多少」，但不能改变「在哪一层能看到什么粒度」。另外注入本身也要花 token 预算，不是免费的。
为什么 DeepStack 很重要

看第 5、6 章的评测表你会发现 Qwen3.5 的强项集中在「细粒度」任务上：OCRBench 93.1（表中最高）、CountBench 97.2（数数）、RefCOCO 92.3（按描述定位图中物体）、OmniDocBench 90.8（文档版式解析）。这类任务的共同点是答案藏在小尺度视觉细节里——恰是一次性注入最容易丢、DeepStack 专门保住的信息。架构选择和 benchmark 强项之间的这条因果线，是理解这个项目的钥匙之一。

第 3 章MRoPE 与时空建模

注意力机制本身是「无序」的——它不知道 token 的先后，更不知道视觉 token 在图里的行列、在视频里的秒数。位置编码负责把这些信息补回去。这一章讲 Qwen VL 线的第二个关键创新：交错 MRoPE，以及建立在它之上的文本-时间戳对齐。

3.1 一维位置编码为什么不够

文本是一维的：token 排成一队，每个位置就是一个序号（第 1 个、第 2 个……）。RoPE（旋转位置编码）给每个位置一个「旋转角度」，让注意力打分天然感知两个 token 的距离。对纯文本，这够了。

图片进来了之后问题来了：一个视觉 token 的位置本质是二维的（第几行、第几列）。硬把图片按行扫成一队，原来上下相邻的两个 patch 在序列里隔了一整行那么远——位置编码会告诉模型「它们离得很远」，这是错误的几何。视频更糟：还要加一维「第几帧」。

MRoPE（Multidirectional RoPE，多维旋转位置编码）的回答：给每个视觉 token 一个三元组位置 (t, h, w)——时间（帧序）、高度（行）、宽度（列）。文本 token 则三个维度取相同的值，退化成普通的一维位置——于是文本和视觉可以在同一套机制里共处。

3.2 三维 MRoPE 怎么工作：为什么是「交错」

实现上，RoPE 的旋转作用在特征向量的不同「频率组」上。多维版本要回答一个设计问题：特征维度怎么在 t / h / w 三个轴之间分配？

  • 分块式（早期 M-RoPE）：把特征维度切成三段，前 1/3 只管 t、中间 1/3 只管 h、最后 1/3 只管 w。简单直接，但高频/低频的分配被割裂：每个轴只拿到一部分频率资源。
  • 交错式（Qwen3-VL 的 Interleaved MRoPE）：把三个轴的位置编码交错分布到特征维度上——这一维归 t、下一维归 h、再下一维归 w，循环排列。这样每个轴都能均匀拿到从高频到低频的全频段资源。

为什么要全频段？直觉是：高频分量编码近处的精细距离，低频分量编码远处的粗略距离。如果某个轴（比如时间轴 t）只分到窄频段，它在「区分相隔很远的两帧」或「区分相邻两帧」上就会变钝。视频理解恰恰两个都要：既要知道「这两件事隔了十分钟」，也要知道「这两个动作是连续两帧」。

打个比方

分块式像给三个部门分办公楼层：t 部门独占 1–10 楼、h 部门 11–20 楼、w 部门 21–30 楼——边界清楚，但有的部门永远拿不到采光好的楼层。交错式像工位按 t-h-w-t-h-w 循环排位：每个部门的人都均匀散布在所有楼层和所有朝向，谁也不吃亏。

类比失效处：比方里的「楼层好坏」是舒适度问题，而 RoPE 频率分配是表达能力问题——不是「吃亏」，而是数学上某些距离会变得不可区分。另外真实特征维度有成百上千个，是三轴「细粒度交织」，远不是 30 层楼三个部门这么粗。

一句话记住：MRoPE = 给每个 token 一个 (t, h, w) 三维坐标；交错布局让三个轴平分全部频率资源，远近都能分辨。

3.2.1 补充：从 RoPE 到 MRoPE 的数学直觉

位置编码要解决的原始问题是：注意力打分只看内容（q·k 点积），不看顺序。RoPE（旋转位置编码）的思路优雅得近乎偷懒——不给向量加位置信息，而是按位置把它「转」一个角度。

把每个 token 的 q、k 向量看成一组二维平面上的指针（每两个特征维度组成一个平面）。位置为 n 的 token，它的指针在第 i 个平面上被旋转角度 θ = n × fi，其中 fi 是这个平面的固定频率。妙处在于：两个 token 做注意力打分时，旋转的作用相互抵消一部分，结果只取决于它们的位置之差（n − m），而不取决于各自的绝对位置——这正是我们想要的「相对距离感知」。用复数写就是一行：乘上 eiθ 是旋转，eiθq · e−iθk = ei(θq−θk)，绝对位置消掉了。

不同频率的维度分工（直觉版）
频率转多快擅长区分类比
高频维度（f 大）位置差 1 就转很大角度相邻位置（近处的精细距离）钟表的秒针
低频维度（f 小）位置差很多才转一圈远距离位置（粗略但量程大）钟表的时针

一组高、低频搭配，就像一套完整的钟表：秒针分针时针合起来，你才能读出任意时刻。这就是 3.2 节「交错布局让每个轴平分全频段」的数学背景——频率资源就是量程资源，哪个轴缺了高频或低频，哪个轴上就会出现「读不出的时刻」。

从 RoPE 到 MRoPE 的推广现在只剩一步：文本的位置是一个数 n，旋转角是 n × f；视觉的位置是三个数 (t, h, w)，那就让不同维度组分别执行 t × f、h × f、w × f 三种旋转——一个 token 的位置向量从「一个角度」变成「一组角度的组合」，三维相对距离 (Δt, Δh, Δw) 同样自然地进入注意力打分。

打个比方

RoPE 像给每个人发一个指南针，指针转过的角度 = 你站的位置。两个人见面，不用报坐标，只要对一下各自指南针的差，就知道彼此隔多远。MRoPE 则是发三个指南针：一个随时间转、一个随行号转、一个随列号转——三个人（t/h/w 三轴）的相对位置同时对得出来。

类比失效处：指南针只有一个频率（转一圈就是一圈），而 RoPE 是一整套不同频率的「指南针组」，每个频率负责一种量程；而且真实旋转发生在高维空间的两两平面上，不是物理空间的方向。另外「对一下差就知道距离」淡化了代价：相对位置信息是在每次点积时现算的，模型并没有一张现成的「距离表」可查。

3.3 文本-时间戳对齐：「第 30 秒」是怎么实现的

有了时间轴位置编码，还差一步才能回答「视频第 30 秒发生了什么」：模型得知道人类说的时间（「30 秒」这串文字）和位置编码里的时间轴之间的换算关系。

Qwen2.5-VL 时代的做法是 T-RoPE：直接把帧的物理时间映射到位置 id。Qwen3-VL 的文本-时间戳对齐更进一步（官方表述为「超越静态 T-RoPE」）：在训练数据里，把视频的帧与显式的时间戳文本（如「30.0 秒」「0:30」）配对监督，让模型学会文字里的时间数字 ↔ 位置编码 t 轴坐标之间的双向换算。于是它可以：

  • 文字 → 时间定位：问「第 30 秒」，它能 attend 到 t 轴对应区间的帧；
  • 时间定位 → 文字：问「猫什么时候跳上桌」，它能输出「约 12.5 秒」这种秒级时间戳答案。
为什么这很重要

视频理解的及格线不是「看懂」，而是「看懂且知道什么时候发生的」。监控告警、体育集锦剪辑、教学视频检索，商业价值全在时间定位上。第 5 章你会看到 Qwen3.5 在长视频 benchmark（MLVU 86.7，表中最高）上的表现——秒级时间定位能力正是长视频任务的核心考察点。没有这个对齐，「256K 上下文装得下两小时视频」也只是一句空话：装得下 ≠ 找得到。

自测题 3.1：假设把视频的帧顺序随机打乱再喂给模型，但保留每一帧原本的 MRoPE 位置编码。模型的视频理解会崩吗？为什么？这个思想实验说明了注意力和位置编码各自负责什么？
先想：注意力打分看的是什么？「序列里的先后顺序」和「位置编码给的坐标」，哪个才真正影响计算？
关键在于：Transformer 的注意力对序列顺序是置换不敏感的——它只通过位置编码感知位置。
第一步这样走：回忆注意力的打分公式：两个 token 的匹配度取决于它们的内容和相对位置（由 RoPE 注入），不取决于它们在内存里排第几。
完整答案：基本不会崩（在不考虑因果掩码干扰的编码场景下）。因为打乱的是存储顺序，而模型感知「时间」的唯一通道是位置编码——每个 token 带着自己原来的 (t, h, w)，注意力照旧能算出「这两帧相邻」「那两帧隔了 30 秒」。这个实验说明：序列顺序对 Transformer 只是容器，位置编码才是位置信息的真实载体。附带推论一：这也是为什么 MRoPE 的设计质量直接决定时空建模的上限；附带推论二：文本那边不一样——语言建模有因果掩码（只能看左边），打乱文本顺序会破坏掩码语义，所以文本不能这么玩。
变式：反过来：帧顺序不动，但把 t 轴位置编码随机重排（h、w 保持正确）。模型会看到什么样的「世界」？它还可能答对「接下来发生了什么」这类题吗？
自测题 3.2：一个任务要求模型「统计视频中球员每次得分的具体秒数」。请拆解这个任务依次用到了本章和上一章的哪些机制（至少四个环节），并指出最可能失败的环节。
先想：从像素到「12.5 秒、47.0 秒、83.5 秒」这串输出，中间每一步是谁在干活？
关键在于：「每次得分」= 事件检测（视觉语义）；「具体秒数」= 时间定位（位置编码 ↔ 文本换算）；「统计」= 不要漏（长序列里多实例召回）。
第一步这样走：沿数据流走一遍：帧 → ViT → merger → 混合序列（带 (t,h,w) 编码）→ LLM 推理 → 输出时间戳文本。
完整答案：环节拆解：① ViT 提取每帧视觉特征（「这是投篮动作」靠它）；② DeepStack 注入保细节（球进筐的瞬间往往是小区域变化）；③ MRoPE 的 t 轴给每帧打上时间坐标；④ 文本-时间戳对齐让模型把「得分时刻」翻译回秒数文本输出；⑤ 长上下文承载整场比赛（256K~1M token）。最可能失败的环节：④ 和 ⑤ 的交界处——视频一长，抽帧就得变稀（token 预算有限），两秒一帧的采样下「进球瞬间」可能恰好落在两帧之间，时间定位精度被采样率锁死；其次是小目标的快速事件（环节①②），球在小分辨率下只有几个像素。这道题想让你建立的感觉是：视频任务的错误常常不是「模型笨」，而是「采样率 × token 预算」这道物理约束先动了手。
变式：如果业务允许你预先知道「得分只会发生在进攻回合」，你能用这条先验把同样 token 预算下的时间定位精度提高吗？怎么做？
自测题 3.3：「文本-时间戳对齐」为什么必须在训练阶段完成，而不能靠推理时的 prompt 技巧（比如在 prompt 里写明「每秒 2 帧」）实现？
先想：prompt 告诉模型的是「规则」，位置编码提供的是「坐标」。知道换算规则，就等于能在坐标系里精确定位吗？
关键在于：模型对 t 轴的感知是隐式的（注意力里的相对旋转角），不是一张写着秒数的坐标表。把「第 30 秒」这串文字和正确的 t 区间挂上钩，是需要学出来的连接。
第一步这样走：类比：告诉一个从没用过地图的人「比例尺 1:50000」，他懂规则，但手没有在地图上量过的经验，第一次量还是会偏。规则和校准是两回事。
完整答案：三个层面。① 表示层面：模型内部没有「t 轴第 60 格」这种显式坐标，只有相对位置编码带来的注意力倾向；让「30 秒」的文字表示与 t≈30s 的帧之间建立稳定注意力通道，只能靠配对数据上的梯度下降学出来。② 精度层面：秒级定位接近回归任务，prompt 规则给的是先验、不是校准——没有任何信号在推理时告诉它「你偏了 3 秒」。③ 输出层面：反向任务（回答「事件发生在 12.5 秒」）更依赖训练——输出格式、数值换算都是学出来的行为。prompt 技巧能做的是「唤起」已训练好的对齐（比如提示它注意时间信息），不能无中生有。这又是「原生多模态」红利的一个例子：对齐做在训练里，推理时才免费。
变式：如果训练数据里的时间戳监督全是整秒（「12 秒」「13 秒」），推理时问「12.5 秒」会发生什么？模型的回答粒度被什么锁死了？

第 4 章语言基座的效率革命

4.1 Gated DeltaNet：把记忆做成固定大小的状态

回忆第 0 章：全注意力要为每个 token 存一份 K、V（KV 缓存），随长度线性膨胀。线性注意力的替代方案是维护一个固定大小的状态矩阵 S，每读一个 token 就更新一次：

St = St−1 · （遗忘/衰减项） + kt vt⊤（写入新信息）

查询时拿当前的 q 去乘状态 S，取回「历史信息的压缩汇总」。不管序列多长，S 的大小不变——这就是「不存 KV 缓存」的含义，也是成本从平方/线性膨胀降为常数占用的根源。

DeltaNet 的「delta 规则」解决的是「写入冲突」：朴素线性注意力直接往状态里加新东西，旧信息被越搅越浑。delta 规则先「擦掉」状态里与当前 key 冲突的旧值，再写入新值——像先在白板对应位置擦干净再写，而不是层层叠涂。Gated（门控）则给衰减加了可学习的开关：模型自己决定每一步遗忘多少、保留多少，而不是用固定衰减率一刀切。

4.2 混合架构：为什么还要保留全注意力

第 0 章的自测题 0.2 已经埋伏了答案：固定状态记不住精确的逐 token 历史。精确检索（「文档第 47 页第三行的数字」「视频第 30 秒那帧」）是全注意力的不可替代项。Qwen3-Next 的方案是层间混合：大部分层用 Gated DeltaNet（便宜、常数记忆），按固定比例插入 Gated Attention 层（精确、负责检索），同时 Gated Attention 层的输出门让模型学会控制检索结果的使用强度。

对多模态场景这个设计尤其合身：视觉 token 数量庞大（长视频动辄几十万），让绝大多数层用线性注意力处理它们，成本才压得住；而「在几十万视觉 token 里精确定位某帧某区域」这种活，留给少数全注意力层干。

打个比方

混合架构像一家医院的病历系统：大部分科室用「摘要病历」（线性注意力）——固定一页纸，每次就诊更新，翻起来快；但医院保留了一个「原始影像档案室」（全注意力层），任何科室遇到摘要解决不了的疑难，可以申请调原始片子逐张看。全靠摘要会误诊，全靠档案室会拖死，混合才是工作系统。

类比失效处：「申请调阅」是人的决策，而混合架构里哪层是线性、哪层是全注意力是硬编码的，模型不能临场决定「这层换成全注意力」。它能调的只是注意力权重和门控。另外 DeltaNet 的状态远比「一页摘要」结构化——它是 key×value 维度的矩阵，查询有精确代数形式，不是自由文本摘要。

4.3 MoE 稀疏度与 MTP

第 0 章讲过 MoE 原理，这里只补这一代的变化：更高稀疏度。397B-A17B 意味着每 token 只用约 4.3% 的参数——同样的每 token 成本下，模型能把知识容量堆到更大。35B-A3B（稀疏度约 11.7）则是这个思路在中小规模的复制：官方宣称它已全面超越 Qwen3-235B-A22B 和 Qwen3-VL-235B-A22B。

MTP（Multi-Token Prediction，多 token 预测）是第二个加速器：训练时让模型不仅预测下一个 token，还同时预测后面好几个。两个收益：训练信号更密（每个位置提供多个监督），推理时可以投机式地一次猜多个 token 再批量验证——生成速度进一步提升。MTP 不是 Qwen 首创，但与混合注意力、MoE 叠加后，三者共同构成「每 token 更便宜」的完整方案。

常见误解

「激活参数只有 17B，所以一张 24 GB 的消费卡就能跑 Qwen3.5-397B-A17B。」——错。第 0 章的 MoE 类比里强调过：全部 397B 参数必须常驻显存（或可随时换入），因为你不知道下一个 token 路由到哪些专家。17B 只决定计算量，不决定显存。397B 参数 BF16 需要约 794 GB 显存（第 8 章详算），单卡无论如何装不下。

自测题 4.1：官方数据说 32K 下吞吐 8.6×、256K 下 19×。请你写出一个「三因素乘法模型」来定性解释这两个数字，并指出哪个因素随长度变化。
先想：吞吐 = 单位时间生成的 token 数。每生成一个 token 的成本由哪几件事决定？
关键在于：把吞吐优势拆成相互独立的乘法因子：每 token 计算量（激活参数比）、每步有效 token 数（MTP 投机解码）、每 token 记忆访问成本（KV 缓存 vs 固定状态）。
第一步这样走：写下 吞吐比 ≈ （计算量比）×（MTP 收益）×（记忆访问比），然后问：三个因子在 32K 和 256K 下各自变不变？
完整答案：模型：吞吐比 ≈ A × M × C(n)，其中 A = 激活参数带来的计算量优势（17B vs 对比方，长度无关）；M = MTP 投机解码的一次多 token 收益（长度基本无关）；C(n) = 记忆访问成本比（KV 缓存读取量 ∝ n vs 线性注意力常数），随长度增大而增大。32K 时 C 还小，8.6× ≈ A × M × C(32K)；256K 时 C 膨胀约 2.2 倍，19.0 ≈ 8.6 × 2.2。这个模型的可证伪点：若将来官方公布 1M 上下文的倍数，此模型预言它应显著大于 19×；若反而持平或下降，说明瓶颈已转移（比如被线性层自身的串行状态更新或通信开销接管）。学会「从架构原理推出可证伪的定量预言」，比记住 8.6 和 19 这两个数重要得多。
变式：如果对比方也换成了混合注意力架构但保持稠密（非 MoE），你预期 256K 下的倍数会落在哪个区间？哪个因子会消失、哪个会保留？
自测题 4.2：Gated DeltaNet 里「门控衰减」和「delta 擦除」听起来都在做「遗忘」。它们的分工有什么不同？各自由什么信号驱动？
先想：一个是全局性的「随着时间慢慢淡忘」，一个是定向的「把这一条旧记录改掉」。哪个是哪个？
关键在于：衰减作用在整个状态上（无差别），delta 擦除作用在与当前 key 相关的特定记忆槽位上（有指向）。
第一步这样走：对照公式：S ← S·g（门控衰减，g 是 0~1 的门）发生在写入之前、作用于整个 S；delta 规则是先算「当前 key 在 S 里已存了什么」，把这部分减掉再写入新值。
完整答案：门控衰减 = 被动的、均匀的时间性遗忘：每过一步，所有旧信息按门控系数打折。它由学习到的门控信号驱动，回答「多久以前的事还值得留」。delta 擦除 = 主动的、定向的内容性更新：当新信息与状态中某 key 槽位的旧内容冲突时，先把旧值精准减去再写新值。它由当前 token 的 key 驱动，回答「这条具体记录该被哪条新记录替换」。缺了前者，状态被远古信息淤塞；缺了后者，同一槽位的新旧信息互相污染（「他把杯子放在厨房……不，移到客厅了」——模型必须能把「厨房」从「杯子的位置」这个槽位里擦掉）。两者结合才让固定大小的状态具备可用的长期记忆。
变式：在一个「先听到 A=1，5000 个 token 后听到 A=2，再过 5000 个 token 被问 A 等于几」的测试里，门控衰减太强和太弱分别会导致什么错误？
自测题 4.3：MTP（多 token 预测）为什么既能加速训练又能加速推理？这两个收益的背后机制是同一件事吗？
先想：训练时被什么限制（每个位置能得到多少监督）？推理时被什么限制（必须串行走多少步）？
关键在于：训练的瓶颈是信号密度，推理的瓶颈是串行步数——MTP 恰好各戳一下，但戳的是两个完全不同的点。
第一步这样走：分别写出来：训练时每个位置 1 份监督 → MTP 后 k 份；推理时每个前向步出 1 个 token → 投机验证后一步最多接受 k 个。
完整答案：不是同一件事，是同一组参数的两份红利。训练侧：普通下一 token 预测每个位置只提供一份监督，MTP 让每个位置同时预测后 k 个 token——监督信号密度成倍增加，模型被迫学习更长期的结构（想猜中后两个词，就得懂句法走向），这是「训练效率/质量」收益。推理侧：生成严格串行，MTP 头一次猜出后续多个候选 token，主模型一次前向并行验证、能接受几个算几个——这是「延迟」收益，本质是内置版投机解码。两者唯一的联系是共享「预测多个未来 token」这组头；瓶颈与收益类型都不同。检验是否真懂的一句话：训练本来就并行，MTP 给训练侧的从来不是并行度——把它也解释成「并行」就说明没分清。

常见误解

「官方表里 Qwen3.5 一半以上的项目是最高分，所以它是当前最强 VLM。」

两个漏洞。第一，选榜：表里有哪 30 个 benchmark 是发布方定的——每家都会把自己强的项目放进表里，这不是阴谋，是行业惯例，但你得意识到这一点。第二，权重：把「30 项里赢 18 项」当成选型依据，等于默认 30 个 benchmark 对你等权——可你的应用可能只跟其中 2 个相关。对你的场景而言，99% 的榜单行都是噪声。

6.3 如何不被榜单带节奏

一套可执行的读表流程：

  1. 先写需求，再看表。把你的场景翻译成最相近的 2–3 个 benchmark（如「看懂扫描发票」≈ OCRBench + OmniDocBench；「操作网页后台」≈ OSWorld/ScreenSpot）。只看这几行。
  2. 查口径：开没开 CI？用的什么解码参数？BrowseComp 为什么有两个数（69.0 上下文折叠 / 78.6 discard-all）？——因为那本来就是两种使用方式的成绩。
  3. 看差距的量级：1–2 分以内的差距基本在同次重跑噪声范围内；5 分以上才可当作稳定结论；12 分（OCRBench 对 GPT-5.2）是代差级。
  4. 警惕缺席：某家没报某项，大概率不是因为忘了。
  5. 能自测就别只信表：拿 50–200 条你自己业务的真实样本跑一遍，比任何 benchmark 都更接近你的上线表现。
为什么「没有全面碾压，只有场景匹配」是本章的核心句

2026 年的头部模型们在通用能力上已经咬得很紧，代差只出现在特定结构的能力域里：Qwen3.5 的代差在 OCR/文档/细粒度视觉（架构红利直接兑现处），Claude 的强项在 Agentic 电脑操作，Gemini 在长上下文与综合推理的均衡性。选型的正确问题不是「哪个模型最强」，而是「哪个模型的强项恰好是我的主场景、弱项恰好我不在乎」。这句话值得写在团队 wiki 上。

一句话记住：先定场景再看榜——和你的应用无关的那几十行分数，无论谁第一，对你都是噪声。

自测题 6.1：某竞品发布，宣称「在 25 个 benchmark 中的 17 个上超越 Qwen3.5」。在相信这个结论之前，你会向对方索要哪四样东西？
先想：「17/25」这个计数里，每个环节都可以被动手脚：25 是怎么选的、17 是怎么赢的、赢多少、怎么跑的。
关键在于：对应的四类信息：选榜依据、每个 benchmark 的双方原始分数（而非只给胜负）、评测口径、以及对你场景的映射。
第一步这样走：把「17/25」拆回原始数据层：逐榜双方分数表、每榜的 CI/参数/提示词口径、差距的置信度。
完整答案：① 完整的逐榜分数对照表（含 Qwen3.5 一侧每个数字的来源与复现方式）——只给胜负计数不给分数，无法判断赢的是 0.5 分还是 15 分。② 25 个榜的选择过程说明——是否包含 OCR/文档这类 Qwen3.5 明显强势的项目？剔除强项后的「17/25」是另一种故事。③ 评测口径：CI 开关、解码参数、prompt 模板、是否使用官方推荐的推理设置——用非默认设置压低对手分数是常见操作。④ 与你的场景最近的那 2–3 个榜上的具体表现。拿到前三个，你自己就能算出第四个。如果对方只能给你「17/25」这个汇总数字，那它的信息量约等于零。
变式：对方补齐了全部数据，且确实在 17 项上赢得扎实，但这 17 项里没有一项与你的场景（扫描文档解析）相关。你该换模型吗？
自测题 6.2：BrowseComp 报了两个数：69.0（上下文折叠策略）/ 78.6（discard-all 策略）。同一个模型同一个榜，为什么有两个成绩？这给你读「单成绩榜单」什么启示？
先想：变化的是模型还是策略？BrowseComp 这种浏览类任务的成绩为什么会敏感地依赖上下文管理策略？
关键在于：浏览 Agent 会积累超长上下文（几十个网页），「上下文装不下时丢什么」直接决定后段推理质量。两种策略就是两种答案。
第一步这样走：把成绩写成 分数 = f（模型， 使用策略）。同一模型，策略不同 → 两个分。
完整答案：两个数测量的是两个不同的「系统」：模型 + 上下文折叠策略的系统得 69.0，模型 + discard-all 策略的系统得 78.6。浏览任务里上下文迅速膨胀，怎么裁剪历史几乎和模型本身一样影响结局——discard-all 高 9.6 分说明该任务上「保留原始搜索结果全文」比「折叠压缩」更值（或折叠实现有信息损失）。启示有三：① 任何单成绩榜单都隐含了一个未声明的使用策略，跨厂商比较时这些隐含策略很少对齐；② 「模型能力」和「系统能力」要分开记账，第 5 章 CI 的讨论在这里复现；③ 自己部署时，这类「策略旋钮」（上下文管理、CI、采样参数）是你不花一分钱模型费就能拿到的性能空间——先把旋钮拧对，再谈换模型。
变式：如果某厂商只报 78.6 而不提策略，你从表格外无法得知用了 discard-all。设计一个你在技术评审会上提的问题，能逼出这个信息？
自测题 6.3：为「HallusionBench 71.4 表中最强」设计一个三问尽调清单，判断这个优势能否迁移到你的「票据审核」场景。

第一步这样走：列出票据审核的典型错误：把不存在的税号「脑补」出来（先验压过证据）→ 正是幻觉类错误；但也可能有「小字看不清」（感知类错误）——后者不归这个榜管。
完整答案：三问清单：① 失败模式匹配吗？我的错误主要是「幻觉」（按先验编造）还是「看不清」（分辨率不足）？HallusionBench 只覆盖前者；若我的主错误是小字识别，应看 OCRBench / V* 而非此榜。② 数据分布接近吗？该榜的图是什么域（自然图像/图表），我的扫描票据是什么域？域差距会放大或缩小表观差距。③ 口径一致吗？71.4 是在什么设置下跑的（CI、解码参数）？我的部署设置能否复现？结论模板：三问皆匹配 → 把该优势记为「先验加分」，进自建评测集验证；任一问不匹配 → 降权或换榜。这套三问可复用到任何 benchmark 的迁移判断。

7.1 transformers 加载

适合调试与小规模实验。以下以 Qwen3-VL 的标准写法为模板（Qwen3.5 沿用同一套 API；安装最新版 transformers 后把模型 ID 换成对应 Qwen3.5 模型即可）：

from transformers import AutoModelForImageTextToText, AutoProcessor
import torch

model_id = "Qwen/Qwen3-VL-32B-Instruct"  # 换成你的目标模型，如 Qwen3.5 对应 ID

model = AutoModelForImageTextToText.from_pretrained(
    model_id,
    dtype="auto",          # 按权重精度加载（BF16）
    device_map="auto",      # 自动切分到可用 GPU
)
processor = AutoProcessor.from_pretrained(model_id)

messages = [{
    "role": "user",
    "content": [
        {"type": "image", "url": "https://example.com/invoice.jpg"},
        {"type": "text", "text": "提取这张发票的抬头、金额和日期，用 JSON 输出。"},
    ],
}]

inputs = processor.apply_chat_template(
    messages, tokenize=True, add_generation_prompt=True,
    return_dict=True, return_tensors="pt",
).to(model.device)

out = model.generate(**inputs, max_new_tokens=512)
print(processor.batch_decode(
    out[:, inputs["input_ids"].shape[1]:], skip_special_tokens=True)[0])

三个要点：device_map="auto" 会在多卡之间自动切分权重（397B 模型没有 8×80GB 级别的卡就别试了，先换小模型）；apply_chat_template 把图文混排消息编成模型训练时见过的格式，手写拼接容易踩坑；图片可以直接给 URL、本地路径或 PIL 对象。

7.2 vLLM 部署

生产环境用 vLLM（连续批处理 + PagedAttention，吞吐高一个量级）。以 35B-A3B 这类中等模型为例：

# 安装：pip install -U vllm（按官方文档选择支持 Qwen3.5 的版本）
vllm serve Qwen/Qwen3.5-35B-A3B \
  --tensor-parallel-size 2 \        # 2 张卡做张量并行
  --max-model-len 262144 \          # 上下文 256K；显存吃紧就调小
  --gpu-memory-utilization 0.9 \    # 显存利用率上限
  --port 8000

起服务后就是标准 OpenAI 兼容接口（http://localhost:8000/v1），第 7.3 节的客户端代码改个 base_url 就能用。部署 397B-A17B 时把 --tensor-parallel-size 提到 8（8×80GB 起步，见第 8 章显存表），或先用官方/社区的 FP8、4-bit 量化版本。

7.3 百炼 API 调用（Qwen3.5-Plus）

零基础设施的路径：阿里云百炼 Model Studio，OpenAI 兼容协议。模型 ID 以控制台为准（形如 qwen3.5-plus）。

# curl 版
curl -X POST https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions \
  -H "Authorization: Bearer $DASHSCOPE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3.5-plus",
    "messages": [{
      "role": "user",
      "content": [
        {"type": "image_url",
         "image_url": {"url": "https://example.com/invoice.jpg"}},
        {"type": "text", "text": "提取发票抬头、金额、日期，输出 JSON。"}
      ]
    }]
  }'
# Python 版（pip install openai）
from openai import OpenAI

client = OpenAI(
    api_key="$DASHSCOPE_API_KEY",  # 建议从环境变量读
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)
resp = client.chat.completions.create(
    model="qwen3.5-plus",
    messages=[{"role": "user", "content": [
        {"type": "image_url",
         "image_url": {"url": "https://example.com/invoice.jpg"}},
        {"type": "text", "text": "提取发票抬头、金额、日期，输出 JSON。"},
    ]}],
)
print(resp.choices[0].message.content)

Plus 版默认 1M token 上下文、内置官方工具与自适应工具调用——长视频、长文档直接整段丢进去，不用自己搭第 8 章那一整套东西。代价：按 token 计费、数据要出你的网络。

怎么选

原型验证 → 百炼 API（十分钟跑通）；数据敏感 / 调用量大 → vLLM 自建（35B-A3B 或 122B-A10B 是甜点区）；研究 / 微调 → transformers + 开源权重。三条路径的客户端代码都是 OpenAI 兼容协议，互相迁移只要改 base_url 和模型名。

7.5 常见报错 FAQ

Q1：加载模型直接 OOM（CUDA out of memory）

先算账再动手：权重显存 = 参数量 × 字节数（第 8 章计算器）。397B BF16 要约 794 GB，单卡绝无可能。三条出路按序尝试：① 降精度（FP8 减半、INT4 再减半，注意细粒度任务先自测掉点）；② 换小模型（35B-A3B 是甜点）；③ 如果是推理中后期才 OOM，多半是 KV 缓存/上下文太长——把 max-model-len 调小、并发调低。

Q2：transformers 报错不识别模型类型（如 KeyError / "model type not recognized"）

几乎可以确定是 transformers 版本过低，还没有收录这个模型架构。执行 pip install -U transformers（必要时加 --pre 或按模型卡要求装指定版本）。模型卡上会写明最低支持版本，以官方模型卡为准。同理，报「处理器/processor 相关错误」时升级 transformers 与 qwen-vl-utils。

Q3：图像输入报错或模型对图片"视而不见"

九成是消息格式问题。正确做法是用 processor.apply_chat_template，图片放在 content 列表里（{"type": "image", ...}），不要把图片路径拼进纯文本 prompt。本地图片可用绝对路径、file:// URL 或 PIL 对象；另外检查图片是否超过处理器的像素上限被静默缩放——OCR 类任务对分辨率敏感，必要时调高 min_pixels/max_pixels。

Q4：vLLM 启动报 "architecture not supported"

你装的 vLLM 版本还不支持该模型架构。新模型发布初期，支持往往先合入主干再进正式 release——按官方模型卡的部署说明升级到指定版本（有时是 pip install -U vllm，有时是装 nightly），以官方模型卡为准。过渡期可以先用 transformers 路径跑通流程，吞吐低一些但功能完整。

Q5：权重下载慢、频繁中断

国内优先走 ModelScope（7.4 节）；坚持 HF 的话设置镜像环境变量（如 HF_ENDPOINT 指向镜像站）。大模型权重几十上百 GB，务必用支持断点续传的工具（modelscope CLI / huggingface-cli download 均支持），别用浏览器直接下。

自测题 7.1：你在 4×80GB（共 320GB 显存）的机器上 vllm serve 397B-A17B 的 BF16 权重，直接 OOM。列出三条能让它跑起来的路径，并按「保真度损失从小到大」排序。
先想：397B BF16 要多少显存？（第 8 章有完整表，先自己估。）320GB 差多少？
关键在于：参数总量是硬约束：397B × 2 字节 ≈ 794 GB。要么降每个参数的字节数（量化），要么加卡，要么换模型。
第一步这样走：量化：FP8 = 397 GB（仍超 320）；INT4 ≈ 200 GB（装得下）。加卡：8×80GB = 640 GB，BF16 也不够，需配合 FP8。换小模型：122B-A10B FP8 ≈ 122 GB，宽裕。
完整答案：按保真度损失排序：① 加卡 + FP8 量化：8×80GB 跑 FP8（约 397 GB），官方有 QAT 量化版本时损失最小（需更多硬件，成本最高）。② 4-bit 量化（约 200 GB，现有 4 卡即可）：现代 4-bit（如 AWQ/GPTQ 系）在多数任务上掉点有限，但对 OCR 这类吃细粒度的任务要自测——恰是 Qwen3.5 的强项区，别默认无损。③ 换 122B-A10B：不是「量化损失」而是「能力天花板降低」，但对很多业务 122B 已过剩。共同提醒：weights 装下只是门票，KV 缓存/状态与激活值还要再吃一块——--max-model-len 别开满 256K 再喊 OOM。
变式：如果业务只需要 32K 上下文，4-bit 量化的 397B 和 BF16 的 122B 你会选哪个？权衡的轴是什么？
自测题 7.2：同一个模型、同一张图、同一句 prompt，transformers 直跑和百炼 API 的结果不完全一样。列出至少四个可能原因。哪些属于「bug 级」（该修），哪些属于「接受即可」？

关键在于：VLM 的输入不只有文字——图片在进模型前会被缩放/归一化，两端的预处理参数可能不同。
第一步这样走：先查解码参数（temperature 是否为 0），再查图片预处理的 min/max pixels，再查隐藏的系统 prompt，最后查模型版本。

8.2 预填充 vs 解码

两个阶段的成本性格（通用原理 + 本站针对 Qwen3.5 的分析）
预填充（prefill）解码（decode）
做什么一口气读完全部输入（含所有视觉 token）一个一个吐输出 token
并行性高（所有位置同时算）低（严格串行）
瓶颈算力（FLOPs）显存带宽（每步要读完全部激活路径权重 + 记忆）
长视频下的角色成本大头：几十万视觉 token 的平方/线性注意力计算相对小头（答案通常几百 token）
Qwen3.5 的针对性设计线性注意力层把平方项压成线性17B 激活 + MTP，每 token 更便宜

运维含义：视频理解类负载是预填充主导——优化方向是批处理打满算力、控制单请求 token 量（抽帧策略、分辨率上限）；聊天/Agent 类负载是解码主导——优化方向是 MTP、量化（降带宽压力）、并发调度。两类负载最好分开部署（prefill/decode 分离是行业通用做法）。

打个比方

预填充像考试时的「读题」：题目（输入）越长读得越久，但读题可以同时调动全部脑力（并行）；解码像「写答案」：必须一个字一个字往外写（串行），手速（带宽）决定速度。Qwen3.5 的三件套里，线性注意力让「读长题」不再随题长变贵得离谱，17B 激活 + MTP 让「写字」更快。

类比失效处：人读题可以跳读略读，模型预填充必须处理每一个 token（除非做稀疏化/前缀缓存）；且模型「写字」时每写一个字都要重新「搬」一遍 17B 权重——人脑没有这种每字重读的带宽开销。比方只适用于「并行 vs 串行」这一点。

8.3 长视频的成本结构

把自测题 0.1 的数字接过来算成本（本站估算）：一段 30 分钟视频，2 帧/秒、每帧 256 token ≈ 92 万视觉 token。纯全注意力模型处理它：注意力打分次数 ~n² 级、KV 缓存几十 GB 起步；Qwen3.5 混合架构下：大部分层线性增长，KV 缓存只剩全注意力层那一份。官方「256K 下 19× 吞吐」放在这个语境里读才完整——长输入场景正是效率优势最大的地方，也是视频理解的典型场景，这两个事实叠在一起就是产品定位。

但别算漏了：1M token 的预填充，即使用线性注意力也仍是千万亿次级的计算量——按 API 计费时这是一笔按 token 收的账。工程上第一道优化永远是少喂 token：降帧率、降分辨率、先做粗筛再精读，然后才轮到架构红利。

一句话记住：先省 token，再谈架构红利；先对齐口径（上下文 × 阶段 × 推理栈），再外推任何吞吐倍数。

自测题 8.1：某业务每天要处理 5000 段监控视频（每段 10 分钟），用 Qwen3.5 判断「是否有异常事件」。粗估每月 API token 费用前，你至少要拿到哪四个数字？并指出哪个数字的可压缩空间最大。
先想：费用 = 段数 × 每段 token 数 × 单价。每段 token 数由哪几个旋钮决定？
关键在于：每段 token = 时长 × 帧率 × 每帧 token。三个因子都是旋钮，不是常数。
第一步这样走：列数字：① 每段时长（10 分钟，已知）；② 抽帧率（未定，比如 1 帧/秒）；③ 每帧 token（未定，取决于分辨率与 merger 压缩）；④ 输入/输出单价（查百炼价格页，注意视觉 token 的计费方式）。
完整答案：四个数字：抽帧率、每帧 token 数（分辨率 × 压缩率的函数）、输入单价、输出单价（加上已知的段数与时长）。量级演示（估算）：1 帧/秒 × 600 秒 × 256 token ≈ 15.4 万 token/段；5000 段/天 ≈ 7.7 亿 token/天；月 ≈ 230 亿输入 token。可压缩空间最大的是帧率：异常检测多数场景 1 帧/秒甚至更低足够（异常通常持续数秒），从 2 帧/秒降到 0.5 帧/秒直接省 75%——比换便宜模型、比砍价都有效。其次是分辨率/每帧 token（只要不漏关键细节）。工程顺序：先用一段真实视频做「帧率-检出率」曲线，找到检出率开始掉的拐点，拐点左侧就是白扔的钱。
变式：再加一个旋钮：先用一个 9B 小模型在端侧做「粗筛」，只把可疑片段送大模型精读。这把成本结构改成了什么样？引入了什么新风险？
自测题 8.2：官方说 256K 上下文下解码吞吐是 Qwen3-Max 的 19×。一位工程师据此把自家服务的预期吞吐也按 19× 做容量规划。这个外推至少犯了哪三个错误？
先想：19× 的测量条件是什么？他的服务和那些条件差在哪？
关键在于：19× 是「256K 上下文、解码阶段、相对特定基线、官方推理栈」的数字。换任何一个条件，倍数都会变。
第一步这样走：逐项对照：他的平均上下文是多少？他的负载是 prefill 还是 decode 主导？他的硬件/框架和官方差多少？
完整答案：错误一：上下文错配。19× 是 256K 处的值；若他的平均上下文只有 4K，适用的是接近 8.6× 那头的数字，甚至还低（短上下文下固定开销占比更大）。错误二：阶段错配。19× 是解码吞吐；若他的业务是长输入短输出（视频理解），瓶颈在预填充，解码倍数跟他无关。错误三：栈错配。官方数字在官方优化的推理栈上测得；他自建的 vLLM 配置、量化方案、并发策略不同，绝对吞吐和相对倍数都会变。附加错误：容量规划该按「你的负载实测」而不是「厂商的相对倍数」——正确做法是用自己的流量 profile 做压测，把官方倍数只当作「值得投入优化」的先验信号。
变式：如果他的业务恰好是「256K 长输入、长输出、与官方同款推理栈」，19× 就可以直接用了吗？还剩哪个变量没对齐？
自测题 8.3：为「日均 2 亿输入 token + 2 千万输出 token」的文档解析业务做选型：自建 vLLM（35B-A3B，INT4，单卡 80GB）vs 百炼 API（Plus）。写出你的决策树和需要收集的数据。

关键在于：成本不是第一闸——合规和能力不达标时，成本比较根本没机会发生。
第一步这样走：先画第一闸：数据能出内网吗？不能 → 直接自建，比较结束。
完整答案：决策树：① 合规闸：数据能否出内网？不能 → 自建（唯一解）。② 能力闸：Plus 与自建小模型在自建评测集上的字段级准确率差多少？差距超业务容忍 → 选达标者（可能倒逼自建上更大模型，重算成本）。③ 成本闸：API 月费 = 2 亿×30×输入单价 + 2 千万×30×输出单价（查实时价格页）；自建月费 = 机器/卡时 + 运维人力折算。注意文档解析是 prefill 主导，容量要按实测 prefill 吞吐估——35B-A3B 激活仅 3B，这个量级可能 1–2 台机器就够。④ 弹性闸：流量有尖峰吗？API 天然弹性，自建要为峰值留闲置容量。⑤ 可控闸：模型版本锁定、行为可复现性，自建更强。需收集的数据：实时单价、自建评测集准确率、单机实测吞吐、流量曲线、运维人力成本。口诀：合规优先，能力兜底，成本决胜，弹性修正。
变式：把业务量改成「日均 200 万输入 token」（降两个数量级），决策树的哪一闸会改变结果？
本章小结

权重显存 = 参数量 × 字节数：397B 旗舰 BF16 约 794 GB、FP8 约 397 GB、INT4 约 200 GB——单卡装不下，需多卡或量化；9B~35B 才是单卡甜区。预填充吃算力、解码吃带宽，优化方向完全不同。长视频成本的第一旋钮永远是「少喂 token」（帧率 × 分辨率），架构红利（线性注意力、17B 激活、MTP）是第二道。所有厂商倍数都要在「上下文 × 阶段 × 栈」三对齐之后才能外推。
